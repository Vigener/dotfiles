### 【Miyabi環境仕様とモジュール】
- **Miyabi-G (演算加速ノード)**: NVIDIA Grace CPU + H100 GPU (GH200)。メモリ120GB。1ノード1GPU。
  - **NVIDIA HPC SDK**: `nvfortran`, `nvc`, `nvc++`. (モジュール `nvidia nv-hpcx` は計算ノードでデフォルトロード済のため記述不要)
  - **CUDA**: `module load cuda` -> `nvcc`
  - **MPI実行**: `mpirun -n ${NODES} --map-by ppr:1:node --bind-to none ./a.out` (Miyabi-Gは1ノード1GPUのため、プロセスバインディング用ラッパースクリプトは不要。環境引継ぎ時は `unset OMPI_MCA_mca_base_env_list` 後 `mpirun -x PATH -x LD_LIBRARY_PATH ...`)
  - **OpenACCプロファイラ**: GPUの使用確認のため、実行時に `NVCOMPILER_ACC_TIME=1 mpirun ...` を付与して組み込みプロファイラを出力させることを推奨。
- **Miyabi-C (汎用CPUノード)**: Intel Xeon MAX CPU。メモリ128GiB。
  - **Intel oneAPI**: `ifort/ifx`, `icc/icx`, `icpc/icpx`. (モジュール `intel impi` は計算ノードでデフォルトロード済のため記述不要)
  - **MPI実行**: `mpiexec.hydra ./a.out`
- **共通 (GCC)**: `module load gcc ompi` -> `gcc`, `g++`, `gfortran`.
- **コンテナ環境**: `module load singularity/4.2.1` を使用して `singularity <command>` を実行。

### 【コーディング・スクリプト作成ルール】

#### 1. ファイルシステムと出力先
- 絶対に `/home` 領域をファイル出力先に指定しないでください。
- ジョブの標準出力・標準エラー出力は `/work/xg26i048/x10752` 領域（ジョブ投入ディレクトリ）に設定してください。
- ジョブ実行中の一時ファイル・作業データの出力先は、**Miyabi-Gの場合は `/local` (NVMe SSD)、Miyabi-Cの場合は `/tmp`** を使用するパス設計にしてください。
- ジョブのステータス確認は、`-u` オプションは使用せず、シンプルに `qstat` コマンドのみを使用すること。

#### 2. OpenACC と GPU-Aware MPI の注意点 (GH200固有)
- **Managed Memoryの無効化**: `#pragma acc host_data use_device` を用いてデバイスポインタを直接MPI関数に渡す「GPU-Aware MPI」を実装する場合、コンパイルフラグに **`-gpu=mem:managed` を絶対に含めないこと**。GH200上で激しい通信遅延（アンチスケーリング）やクラッシュの原因となる。
- **通信と計算のオーバーラップ**: 究極のスケーリングを目指す場合は、同期通信ではなく非同期通信（`MPI_Isend/Irecv`）とOpenACCの非同期キュー（`async`）を組み合わせて通信待ち時間を隠蔽する設計を提案すること。

#### 3. Makefileの作成
- Miyabi-GかMiyabi-Cかに応じて適切なコンパイラを選択してください。
- NVC++ 推奨フラグ: `-fast -Mconcur` / Intel 推奨フラグ: `-axSAPPHIRERAPIDS,CORE-AVX512`
- バイナリは `bin/`、実行結果は `out/` など、ディレクトリを散らかさないように `mkdir -p` を含むルールを作成してください。

#### 4. PBSジョブスクリプトの作成
- **必須ディレクティブ**:
  - `#!/bin/bash`
  - `#PBS -q <キュー名>` （例: G用は `debug-g`, `regular-g`、C用は `short-c` 等）
  - `#PBS -l select=<ノード数>`
  - `#PBS -l walltime=<HH:MM:SS>` （いかなるテストジョブであっても、無限ループ等によるトークン浪費を防ぐため、必ず **3分間 (`00:03:00`) の安全装置** を設定。長時間の実行が必要な本番計測時のみユーザーの許可を得て延長する）
  - `#PBS -W group_list=xg26i048` （必須。トークン消費用）
  - `#PBS -j oe` （標準出力とエラー出力を結合）
- **安全なスクリプト設計**:
  - `set -euo pipefail` を推奨。マルチバイト文字（日本語）はスクリプトやパスに一切含めない。
  - `cd ${PBS_O_WORKDIR}` を必ず実行し、投入ディレクトリに移動してから処理を行う。
  - **構文エラーの防止**: `#PBS` ディレクティブと同じ行にインラインコメント（例: `#PBS -l select=1 # コメント`）を記述すると構文エラーになるため、絶対に書かないこと。

#### 5. エージェントの自律実行と段階的テストフロー (Guardrails)
エージェントはコード作成後、ユーザーに手動実行を促すのではなく、`run_command` (ssh) を用いて **自律的にrsync転送、コンパイル、qsub投入、ステータス確認** を行うこと。
その際、絶対にいきなり大規模なジョブを投入せず、以下の段階的ステップを厳守し、各ステップごとにユーザーの合意と結果の安全確認を行うこと。

1. **極小サイズテスト (2ノード)**: 数秒で終わる極小問題サイズ（例: N=64）でデッドロックが起きないか確認。
2. **極小サイズスケーリング (1〜4ノード)**: 同様に極小サイズで、ノード数を変えた複数ジョブを投入。
3. **本番スケーリングテスト (1〜8ノード以上)**: 極小テストが全て成功した場合のみ巨大サイズを投入する。

※ **複数ジョブの同時投入** を行う場合は、1つのPBSジョブスクリプト内で多数のノードを占有してループするのではなく、「ノード数ごとに個別のジョブスクリプトを動的に生成し、それぞれ `qsub` させるシェルスクリプト」を作成し実行すること。
