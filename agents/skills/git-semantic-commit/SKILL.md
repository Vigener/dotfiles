# git-semantic-commit

## Overview

現在のワークスペース（カレントリポジトリ）の変更内容を `git status` で確認し、
**意味的なまとまりごとに自動でグループ分け**して Conventional Commits 形式でコミットし、
`git push` まで完結させるスキル。

コミットメッセージは日本語で記述し、人間・AI の両方が後からコミット履歴を検索・追跡しやすい形式にする。

## Dependencies

なし（外部スキル・スクリプト不要）

## Quick Start

ユーザーが「コミットして」「変更をまとめてコミット」等と言ったら、このスキルを発動する。

## Workflow

### ステップ 1: 現状把握

```bash
git status
git diff --stat
```

- `git status` で modified / untracked ファイルの全一覧を取得する
- `git diff --stat` で各 modified ファイルの変更概要（追加・削除行数）を把握する
- 変更内容が不明瞭なファイルは `git diff <file>` で中身を確認する
- **ワークスペースがクリーンな場合**は「コミットする変更がありません」と報告して終了する

### ステップ 2: グループ分け

以下の優先順位でファイルをグループ化する。

#### 基本ルール

1. **論理的に同一の変更はひとまとめにする**（例: `launcher.ts` の変更に伴う `README.md` の更新などは、無理に分けずにメインとなる変更のコミットに含める）
2. **無関係な変更は分割する**（同一 type であっても、機能領域(scope)や目的が全く異なれば別コミットにする）
3. **密結合ファイルはひとまとめ**（例: `.h` と `.c` のペア、コードとそのテスト、コードとそのドキュメント）

#### type 選択ガイド

| type | 使いどころ |
|---|---|
| `feat` | 新機能・新スクリプト・新しい実装コード |
| `fix` | バグ修正・誤り訂正 |
| `docs` | wiki・README・メモ・ドキュメントの追加・変更 |
| `refactor` | 動作を変えない構造整理・リネーム |
| `chore` | ビルド設定・Makefile・`.gitignore`・ツール設定ファイル |
| `ci` | CI/CD 設定（GitHub Actions 等） |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `style` | フォーマット・空白・コードスタイルのみの変更 |

### ステップ 3: コミットメッセージの生成

#### 書式

```
<type>(<scope>): <description>
```

- **scope**: 変更が属するディレクトリ名・コンポーネント名（省略可）
- **description**: 日本語・命令形（「追加」「修正」「削除」）・50文字以内を目安
- **AI 検索性向上のため**: 変更に関わる重要キーワードを括弧内に付加する

#### 良いメッセージの例

```
docs(wiki): SSH設定ガイドを追加 (ControlMaster, Multiplexing)
feat(projects/pingpong): MPI pingpong テストを実装
chore: ビルド設定を追加 (clangd, Makefile, rsyncignore)
fix(context): Miyabi スキル定義の誤りを修正
docs: current_state を更新
```

#### 避けるべき例

```
# NG: 情報が少なすぎて検索できない
update files
fix bug

# NG: 無関係な変更を雑に混ぜている
feat: 〇〇機能追加と、関係ないバグ修正とドキュメント更新
```

### ステップ 4: グループごとにコミット

各グループに対して順番に実行する:

```bash
git add <グループに属するファイル...>
git commit -m "<type>(<scope>): <description>"
```

- `git add .` は使わない。**必ずファイルを明示的に指定する**
- コミット後、次のグループへ進む

### ステップ 5: プッシュ

```bash
git pull --rebase
git push
```

- 全グループのコミット完了後に、リモートの最新変更を取り込んでから一括でプッシュする
- もし `git pull --rebase` でコンフリクトが発生した場合は、ユーザーに報告して解決を促す
- プッシュ成功後、実行したコミットの一覧をユーザーに報告する

#### 報告フォーマット例

```
✅ 3件のコミットをプッシュしました:

1. docs(wiki): SSH設定ガイドを追加 (ControlMaster, Multiplexing)
2. docs: Miyabi wiki・context を更新
3. chore: ビルド設定を追加 (clangd, Makefile, pingpong_test)
```

## エラーハンドリング

| 状況 | 対応 |
|---|---|
| ワークスペースがクリーン | 「コミットする変更がありません」と報告して終了 |
| `~/.ssh/control_sockets/` が存在しない | `mkdir -p ~/.ssh/control_sockets && chmod 700 ~/.ssh/control_sockets` を実行してリトライ |
| `git push` が失敗（その他） | エラー内容を診断・報告し、解決できる場合は再試行 |
| マージコンフリクトあり | コミットを中断し、ユーザーに報告して解決を促す |
| ファイルの分類が不明確 | 最も近い type に分類し、コミットメッセージに補足キーワードを追加 |

## Common Mistakes

1. **`git add .` を使わない**: 関係のないファイルを誤ってコミットしないよう、必ずファイルを明示指定する
2. **過度な分割**: 実装コードとそれに伴うドキュメント更新など、論理的にひとまとまりの変更を「用途が違うから」と無理に分割しないこと
3. **scope の過度な省略**: scope を省略するとコミット履歴の検索性が下がる。ディレクトリ名で明示する
