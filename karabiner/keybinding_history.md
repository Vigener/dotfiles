# Karabiner-Elements キーバインド変更履歴と経緯

## 2026年7月6日: Zellij導入に伴う `Ctrl+Q` -> `Cmd+W` 廃止と `英数+W` の再定義

### 背景と課題
ターミナルマルチプレクサとして Zellij を使い始めた際に問題が発生した。
Zellij ではデフォルトで `Ctrl+Q` が Quit（終了）に割り当てられているが、Karabiner-Elements にて `Ctrl+Q` を `Cmd+W` (タブを閉じる) にマッピングしていたため、Zellij の終了ショートカットを押すと、Zellij にキー入力が渡る前に Zed ターミナルのタブ自体が閉じられてしまう事態になった。

### 以前の `Ctrl+Q` -> `Cmd+W` 設定の経緯と意図
この特殊なマッピングが行われていたのには、以下の経緯があった。
1. **Windows時代（Vivaldi使用時）:**
   Windowsでは標準で `Ctrl+W` が「タブを閉じる」機能を持っていた。
   Vivaldi の「パネル開閉」機能には `Alt+W` が割り当てられていたが、左手で押しやすいように `英数キー+W` をこの機能に割り当てていた。
2. **Macへの移行:**
   Mac に移行した際、Emacsキーバインドが有効な環境では `Ctrl+W` が「単語削除」に取られてしまうことを知った。
   そこで、「タブを閉じる」ための `Cmd+W` をどう押しやすくするかが課題となった。
3. **`英数+W` の不採用:**
   `Cmd+W` を `英数+W` に割り当てる案も検討したが、Vivaldi で頻繁に使っていた「パネル開閉」（トグル操作で安全）と同じキーボード位置に、「タブを閉じる」という破壊的な操作（`Cmd+Shift+T` で復元可能とはいえ）を割り当てるのは、誤爆による心理的負担が大きいと判断し却下された。
4. **`Ctrl+Q` への割り当て:**
   結果として、Windowsの `Ctrl+W` と位置が近くマッスルメモリーへの認知負荷が低い `Ctrl+Q` に白羽の矢が立った。また、`Cmd+Q` で「アプリを閉じる」、`Ctrl+Q` で「タブを閉じる」というように、「閉じる (Quit)」という概念が `Q` キー周辺にまとまるという納得感もあったため、この設定が定着していた。

### 今回の意思決定
Vivaldi をメインブラウザとして使用しなくなった現在、`英数+W` （かつてのパネル開閉トグル）を使用する機会はほぼなくなった。そのため、過去の「誤ってタブを閉じてしまう」というマッスルメモリーによる認知負荷は、もはや問題にならないと判断。

Zellij のショートカットを変更する、または Zed のショートカットを大幅に変更するという選択肢も検討したが、システム全体に及ぶ副作用や設定の複雑化を避けるため、Karabiner-Elements の設定を修正するのが最も妥当（丸い）という結論に至った。

### 変更内容
1. **廃止:** `Ctrl+Q` を `Cmd+W` に変換するマッピングを削除（Zellij の `Ctrl+Q` が正常に動くようにする）。
2. **新規:** `英数+W` を `Cmd+W` (タブを閉じる) に割り当て。これにより、ホームポジションから手を崩さずにタブを閉じる操作を実現しつつ、Zellij との競合を解消する。

## 2026年7月6日: 英数レイヤーにおける `S`, `F`, `A`, `E` キーの役割についての考察と方針

### 背景
英数レイヤーは「Win/Mac共通のCmd(Ctrl)系ショートカット」と「Vim由来(hjkl)のキャレット移動」を統合するレイヤーとして機能している。
その中で、`Cmd+S` (保存) や `Cmd+F` (検索) を英数レイヤーに統合すべきかという疑問が生じた。

### 現在の割り当てとその理由
現在、`英数+S` は「行頭へ移動」、`英数+F` は「行末へ移動」に割り当てられている。
*   **行頭/行末移動の重要性:** 非常に使用頻度が高く、ホームポジションから指を離さずに（`A`や`E`に伸ばさずに）アクセスできる `S` と `F` は、独自の最適解として定着している。
*   **保存(Cmd+S)の不要論:** 現代の開発環境やアプリでは「オートセーブ」が基本であるべきであり、手動保存の頻度は低いため、一等地のキーを割り当てる優先度は低い。
*   **検索(Cmd+F)の優先度:** 検索は便利だが、全選択(`Cmd+A`)などに比べると使用頻度は一段落ちる。

### Emacsバインド(A, E)への移行を却下した理由
行頭/行末移動をEmacs本来の `A` と `E` に移し、`S`と`F`を空ける案も検討されたが、以下の理由で却下された。
1.  **VimとEmacsの混在:** 移動キーにVim(`hjkl`)とEmacs(`a/e`)が混ざるのは認知的に不自然。
2.  **`Cmd+A` との競合:** `英数+A` は「全選択(`Cmd+A`)」として極めて重要かつ頻繁に使われるため、行頭移動で上書きするわけにはいかない。

### ブラウザ(Dia)固有のショートカットに関する考察
現在のメインブラウザである Dia では、`Cmd+S` (タブバートグル) や `Cmd+E` (AIチャットトグル) という独自のショートカットが多用される。
これを英数レイヤーで操作したくなる誘惑はあるが、以下の理由から「グローバルな英数レイヤー」を Dia に寄せすぎるのは危険と判断。
*   **ブラウザの変遷:** Vivaldi から Dia に移ったように、ブラウザは将来変わる可能性がある。一時的なメインツールのために、汎用的なベースレイヤーの設計を歪めるべきではない。

## 2026年7月6日: 英数+Dの「一行選択」復活とMac標準Emacsバインドへの移行

### 背景と経緯
当初、「英数+D」には「一行選択」を割り当てていたが、Vimの `dd` のような操作感を求めた結果、副作用として `Cmd+D`（ブラウザのブックマーク保存、エディタでのマルチカーソル選択など）が本来の位置で使えなくなるという懸念があり、一度は標準の `Cmd+D` として解放した。
当時、`cmux` (ターミナルマルチプレクサ) を活用する方針を立てており、そこでの `Split right` 等の操作に `Cmd+D` などの標準ショートカットが必要になる想定だった。

### 今回の意思決定
1. **Zellij 優先の方針:** 複数エージェントを動かすために `cmux` の導入を検討していたが、学習コストや現在の運用頻度を考慮し、まずはすでにセッション保存などで活用している `Zellij` (SSH先) + `Zed` の運用を優先することにした。これにより、`cmux` 固有のショートカット (`Cmd+D` 等) の必要性が低下した。
2. **利用頻度とスピードの優先:** ブラウザ等での `Cmd+D` (ブックマーク) は頻繁に使う操作ではない。一方で、「一行選択」は非常に高頻度で使うため、ホームポジションの一等地である「英数+D」を「一行選択」に戻す方が、作業スピードの向上に大きく貢献すると判断した。
3. **堅牢なマクロの実装:** 以前の「一行選択」マクロ（`Home` -> `Shift+End`）は、ブラウザなどのテキストエリアで「文頭・文末」に飛んでしまう不安定さがあった。これを解決するため、今回はMacのシステム標準でサポートされているEmacs系のカーソル操作（`Ctrl+A` で行頭へ、`Shift+Ctrl+E` で行末まで選択）を裏側で発火させる堅牢な実装に変更した。

### 追記 (Zedとの競合修正)
`Ctrl+Shift+E` が Zed エディタの「エクスプローラーを開く」ショートカットと競合することが判明したため、エディタの操作感を阻害しないよう、「英数+D」の内部マクロを `Ctrl+A` (行頭) -> `Shift+End` (行末まで選択) の組み合わせに修正した。

## 2026年7月7日: 行操作を「論理行(Emacsバインド)」から「視覚行(Mac GUIバインド)」へ回帰
`Ctrl+A/E` (Emacsバインド) は論理行（段落全体）に作用するため、折り返しがある長いテキストでの微調整に不便であることがわかった。また、`Ctrl+A` が非ネイティブアプリ（Word等）で「すべて選択」として誤作動するリスクもあった。
そのため、見た目通りの「視覚的な一行」を操作できるMac標準のGUIバインド（`Cmd+←/→`）を再度採用することとした。
- `英数+S`: `Ctrl+A` -> `Cmd+←`
- `英数+F`: `Ctrl+E` -> `Cmd+→`
- `英数+D` (一行選択): `Ctrl+A -> Shift+Ctrl+E` -> `Cmd+← -> Shift+Cmd+→`
